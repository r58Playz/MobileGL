# MobileGL native Minecraft differential harness

This harness keeps discovery and reduction separate:

1. Launch the real game through the native GLX bridge and Dawn/Vulkan backend.
2. Enter a deterministic local world manually and note the first broken scene.
3. Relaunch the same Prism instance under stock OpenGL plus `apitrace trace`.
4. Trim a whole rendered frame with `gltrim -f`; do not capture WebAssembly API calls.
5. Replay the native GL trace through DirectVulkan and DirectWebGPU and run
   `compare_frames.py`, or use `run_differential.py --localize` to bisect the first
   divergent replay call.

The default gates are SSIM >= 0.99, no more than 1% of pixels with any channel
delta over 16, and no validation/device-loss/assertion markers in either log.

## Agent investigation guide

Use this section when diagnosing a report from the native harness. Do not begin
by changing renderer code. First establish how far the call chain gets and save
the first failing boundary.

### Know which environment is under test

This directory is a **native Linux/X11 harness**. Its bridge uses `LD_PRELOAD`,
`LD_LIBRARY_PATH`, `dlopen`, and `dlsym` to impersonate `libGL.so.1` and
`libGLX.so.0`. Those mechanisms are intentionally native-only.

The production IKVM/Emscripten build has no usable ELF dynamic loader. Patched
LWJGL uses `StaticLinkLoader`, `JVM_LoadLibrary`, and `JVM_FindLibraryEntry`,
whose tables are generated by `tools/ikvm/gen-static-libs.py`. Once LWJGL has
obtained `glXGetProcAddress` or `eglGetProcAddress` from that static table,
per-GL-function lookup goes through emscripten-glfw's backend dispatcher. Never
propose `LD_PRELOAD`, raw `dlsym`, or `apitrace trace` as a WASM fix.

When a native fix changes exported bridge or backend symbols, determine whether
the analogous WASM archive changed too. If it did, regenerate the consumer's
static-library registry. A native bridge success alone does not prove WASM
lookup is correct.

### Call chain and ownership

The expected native call chain is:

```text
Minecraft / LWJGL / GLFW
  -> libGL.so.1 or libGLX.so.0 alias
  -> libMobileGLGLX.so (GLX facade and direct GL 1.x trampolines)
  -> optional libSimpleFPEWrapper.so (legacy fixed-function frontend)
  -> libMobileGL.so (core GL implementation)
  -> DirectVulkan or native Dawn DirectWebGPU
  -> X11 window
```

Important ownership rules:

- The bridge owns the public GLX lifecycle and proc-address functions.
- With `MOBILEGL_FRONTEND=sfpew`, fixed-function calls go to SFPEW first.
- SFPEW's downstream resolver must use the explicit `gMobileGl` handle. Using
  `RTLD_DEFAULT` or an interposed public GL symbol can route back into the bridge
  and recurse indefinitely.
- Core calls not implemented by SFPEW fall through to MobileGL.
- DirectVulkan is the renderer reference, not a different GL frontend. Keep the
  same frontend, game configuration, and scene when comparing it to WebGPU.
- On native LWJGL, some OpenGL 1.x functions can be resolved directly from the
  `libGL.so.1` handle. This is why the bridge exports direct trampolines such as
  `glAlphaFunc`, in addition to returning them from `glXGetProcAddress`.

### Relevant files

| File | Responsibility |
| --- | --- |
| `glx_bridge.cpp` | GLX facade, EGL lifecycle, native symbol routing, SFPEW initialization, swap logging |

Also inspect `SimpleFPEWrapper/SimpleFPEWrapper/getter.cpp` when LWJGL capability

corresponding WASM route.

### Minimum evidence to collect

Ask for or record all of the following before editing code:

1. Exact Minecraft, Java, LWJGL, mod-loader, and Prism versions.
2. Exact wrapper command and the values of `MOBILEGL_BACKEND_TYPE` and
   `MOBILEGL_FRONTEND`.
3. Full combined stdout/stderr from process start through failure. A clipped
   exception without the bridge startup lines is insufficient.
4. `build-dawn/mobilegl-runtime.log` or the matching build directory's log.
5. Whether DirectVulkan with the same frontend and scene succeeds.
6. The last successful bridge checkpoint: load, context creation, make-current,
   surface creation, or swap.
7. For a visual mismatch, screenshots from both backends at the same window
   size, world position, camera, FOV, time, weather, render distance, GUI scale,
   resource packs, and frame phase.

For a direct command, capture a high-signal log with:

```sh
MOBILEGL_GLX_TRACE=1 \
MOBILEGL_GLX_TRACE_PROCS=1 \
MOBILEGL_BACKEND_TYPE=DirectWebGPU \
MOBILEGL_FRONTEND=sfpew \
./launch.sh <java-or-launcher-command> 2>&1 | tee native-harness.log
```

`MOBILEGL_GLX_TRACE_PROCS=1` is intentionally noisy. Enable it only until the
first missing or wrongly routed function is identified.

### Evidence ladder

Read the log in this order. Each line proves a different layer:

1. `bridge loaded into process` proves `LD_PRELOAD` reached that process.
2. `loaded MobileGL from ...` proves the explicit backend library opened and
   its required EGL exports resolved.
3. `intercepted GLX context creation` proves GLFW/LWJGL selected the bridge's
   GLX implementation.
4. `created WIDTHxHEIGHT surface` proves the X11 drawable became a MobileGL EGL
   window surface.
5. `MobileGL context is current` proves `eglMakeCurrent` succeeded and SFPEW
   initialization was attempted when selected.
6. `glGetString(...)` proves at least one GL call reached the selected frontend.
7. `swap #N ... -> ok` proves the application is presenting through MobileGL.

A later checkpoint does not prove rendering correctness. For example, successful
swaps with a black window usually mean interception and presentation work, while
draw state, shaders, attachments, or frontend translation are wrong.

### Failure decision tree

#### No `bridge loaded into process`

- Confirm Prism's Wrapper command is the absolute path to `launch.sh`, not a
  command that merely launches Prism itself outside the instance wrapper.
- Confirm the wrapper is executable and its echoed arguments contain the Java
  game command.
- Check for sanitized loader variables, setuid binaries, Flatpak/container
  boundaries, or a launcher that starts the game in a different environment.
- Do not conclude that missing `LD_PRELOAD` is the only cause: LWJGL may open a
  specific `libGL.so.1` handle, which is why the bridge directory must also be
  first in `LD_LIBRARY_PATH`.

#### Bridge loads, but no context creation

- Enable proc tracing and determine which GLX entry point was requested last.
- Verify the bridge aliases exist beside `libMobileGLGLX.so`:

  ```sh
  ls -l build-dawn/tools/native_harness/libGL* \
        build-dawn/tools/native_harness/libMobileGLGLX.so
  nm -D build-dawn/tools/native_harness/libMobileGLGLX.so | \
    rg 'glX(Create|Choose|GetProc|Make|Swap)'
  ```

- Force X11/XWayland. The current bridge does not implement a native Wayland
  window-system path; `launch.sh` clears `WAYLAND_DISPLAY` for this reason.
- If SDL is involved, verify `SDL_OPENGL_LIBRARY`, `SDL_EGL_LIBRARY`, and
  `SDL_VIDEO_FORCE_EGL` in the launcher trace.

#### Context creation succeeds, but make-current fails

- Compare Dawn and Vulkan logs. A failure in both points toward GLX-to-EGL
  lifecycle or drawable/config handling; a failure in only one points toward
  backend initialization.
- Check for `eglChooseConfig`, context version, surface creation, and native
  window errors before changing GL dispatch.
- Ensure the bridge and `libMobileGL.so` came from the same build directory.
  Mixing `build-dawn` and `build-vulkan` bridge/backend artifacts is unsupported.
- Do not reuse a log from a prior run; `launch.sh` writes a build-specific
  `mobilegl-runtime.log`.

#### Make-current succeeds, then LWJGL reports a missing GL function

- Record the exact first missing function and whether LWJGL obtained a nonzero
  pointer for it during capability creation.
- With SFPEW, query `GL_CONTEXT_PROFILE_MASK` and `GL_CONTEXT_FLAGS`. LWJGL must
  see a compatibility profile and no forward-compatible bit or it intentionally
  discards deprecated entry points such as `glAlphaFunc`.
- Check both native lookup routes: direct bridge export and
  `glXGetProcAddress`. A function working through only one route is not enough.
- Inspect the function signature. WebAssembly indirect calls are signature
  checked; a symbol with the right name but a K&R or otherwise incorrect
  declaration in `gen-static-libs.py` can trap in WASM even though native works.

#### Crash or hang immediately after SFPEW initialization

- Suspect resolver recursion before suspecting renderer code.
- The SFPEW downstream function must first `dlsym(gMobileGl, name)`, then use
  MobileGL's explicit `eglGetProcAddress`. It must not resolve via the global
  namespace or the bridge's public GL symbols.
- Use a debugger backtrace and look for repeating bridge/SFPEW frames.
- Verify `SFPEW_DEFER_INIT=1`; initialization before a context is current can
  produce misleading missing-function failures.

#### Swaps succeed, but the window is black

- Treat this as a renderer/frontend issue, not an interception issue.
- First run the same scene with DirectVulkan and the same `core`/`sfpew`
  frontend. If both are black, reduce the GL/frontend path. If only WebGPU is
  black, capture and replay a stable frame.
- Check whether `glClear` changes the window. A visible clear but missing world
  narrows the problem to draw submission, state, shader translation, or resource
  binding rather than surface presentation.
- Look for shader compilation, WebGPU validation, device-loss, framebuffer
  completeness, and unsupported-enum messages in the MobileGL log.
- Do not infer correctness merely from `swap -> ok`; it only reports successful
  presentation.

#### Rendering differs from DirectVulkan

- Capture the known-good Vulkan run first using `capture.sh` as the Prism
  wrapper, then minimize to one complete stable frame.
- Replay the identical trace through both backends and compare `actual.png`.
- Localize only after confirming the divergence is repeatable. Binary search in
  `run_differential.py --localize` assumes the mismatch persists after its first
  occurrence; transient or alternating errors need manual call-range sampling.
- At the first divergent call, inspect state established before that call, not
  only the call itself. Texture uploads, pixel-store state, buffer mapping, and
  framebuffer attachments commonly fail earlier than the visible draw.

#### Apitrace crashes, bypasses the bridge, or captures nothing

- Use `capture.sh` as the wrapper. It intentionally puts apitrace before the
  MobileGL bridge.
- Do not run `apitrace trace ./launch.sh`; that reverses interposer ordering.
- System apitrace is acceptable. The vendored copy is not required unless the
  installed version cannot trace the process.
- The trace is a native OpenGL trace. Do not attempt to capture browser/WASM GL
  calls with system apitrace.
- Preserve the full trace until a trimmed frame reproduces correctly on Vulkan
  and incorrectly on WebGPU.

### Native-to-WASM follow-through

After fixing a native problem, explicitly classify the change:

- **GLX/X11 lifecycle only:** native harness-specific; add a native regression.
- **SFPEW profile, state, or fixed-function translation:** shared behavior;
  rebuild and test the Emscripten SFPEW archive too.
- **MobileGL core or DirectWebGPU:** shared renderer behavior; run the browser
  WebGPU harness in addition to native Dawn.
- **Exported symbol or proc-address routing:** regenerate the combined WASM
  archive and `gen-static-libs.py` output, then test through patched
  emscripten-glfw. `nm` output alone is not a runtime test.

For pthread Emscripten artifacts, serve the browser harness with
`tools/web_harness/serve.py`. A plain `python3 -m http.server` omits COOP/COEP,
so `SharedArrayBuffer` is unavailable and WASM can fail before `main`.

The expected WASM lookup chain is:

```text
patched LWJGL LinuxLibrary
  -> JVM_LoadLibrary / JVM_FindLibraryEntry static table
  -> glXGetProcAddress or eglGetProcAddress bootstrap pointer
  -> emscripten-glfw gl_backend_get_proc_address
  -> SFPEW when selected
  -> MobileGL
  -> browser WebGPU
```

## other

Build the complete native harness from the MobileGL repository root:

```sh
tools/native_harness/build_all.sh
```

This creates `build-dawn/` and builds MobileGL, pinned Dawn, the GLX bridge,
trace replay, and SFPEW. The initial Dawn checkout downloads its pinned source
and dependencies. Use `--jobs N` to limit parallelism or `--dawn-source PATH`
to reuse an existing Dawn checkout.

`minecraft_matrix.json` is the initial era matrix. Versions through 1.16.5 use
the SFPEW frontend; newer versions enter MobileGL core directly. Traces stay local
until they are deterministic and minimized, then their archives and goldens can be
promoted to Git LFS and registered in `tools/trace_replay/trace_cases.json`.

Build with `MOBILEGL_NATIVE_WEBGPU=ON` and
`MOBILEGL_BUILD_NATIVE_HARNESS=ON`, then launch Prism itself through the
preload bridge. Select `sfpew` only for the four legacy matrix entries:

```sh
python3 tools/native_harness/launch_prism.py \
  --bridge build-dawn/tools/native_harness/libMobileGLGLX.so \
  --mobilegl build-dawn/libMobileGL.so --frontend core --trace -- prismlauncher
```

The launcher places the bridge directory first on `LD_LIBRARY_PATH` as well as
using `LD_PRELOAD`. This is required because GLFW/LWJGL can open `libGL.so.1`
and `libGLX.so.0` directly and resolve symbols against those specific handles.
The bridge build provides aliases for both library families. With `--trace`,
successful interception prints `[mobilegl-glx]` context, surface, and swap
messages to the game log. The SDL environment overrides remain useful for SDL
applications tested with the same wrapper, but Minecraft 26.2 creates its window
with GLFW's native OpenGL context API.

For a legacy instance, replace `--frontend core` with:

```sh
--frontend sfpew --sfpew build-dawn/sfpew/libSimpleFPEWrapper.so
```

The bridge implements the GLX context/window lifecycle used by LWJGL 2 and
GLFW/LWJGL 3, but creates MobileGL EGL contexts and surfaces underneath. It is
currently X11/XWayland-only; native Wayland launcher windows are outside the
first harness slice.

## Live DirectVulkan comparison

`launch.sh` selects DirectWebGPU from `build-dawn` by default. Select the
reference backend with an environment variable; the script automatically uses
`build-vulkan` while keeping the same bridge behavior and Minecraft configuration:

```sh
MOBILEGL_BACKEND_TYPE=DirectVulkan ./launch.sh <java command...>
MOBILEGL_BACKEND_TYPE=DirectWebGPU ./launch.sh <java command...>
```

For Prism's Wrapper command field, use either:

```text
env MOBILEGL_BACKEND_TYPE=DirectVulkan MOBILEGL_FRONTEND=sfpew /absolute/path/to/MobileGL/launch.sh
env MOBILEGL_BACKEND_TYPE=DirectWebGPU MOBILEGL_FRONTEND=sfpew /absolute/path/to/MobileGL/launch.sh
```

`launch.sh` uses the backend-independent SFPEW library from
`build-dawn/sfpew/libSimpleFPEWrapper.so` for either renderer. Set
`MOBILEGL_FRONTEND=core` for Minecraft versions that do not need fixed-function
emulation, or override the library with `MOBILEGL_SFPEW_LIBRARY`.

Keep window size, world, position, camera, FOV, GUI scale, time, weather,
resource packs, and render distance fixed between runs.

## Capture Minecraft through the wrapper

`capture.sh` uses `MOBILEGL_APITRACE` when set, otherwise a system `apitrace` on
`PATH`, and finally the vendored copy. `build_all.sh` skips the vendored apitrace
build when the system command is available; set `MOBILEGL_BUILD_BUNDLED_APITRACE=ON`
to force it. Set `capture.sh` as Prism's
Wrapper command. It places apitrace in front of the MobileGL bridge, so the trace records
Minecraft's GL API stream while the selected MobileGL backend still renders it.
Capture the known-good DirectVulkan run first:

```text
env MOBILEGL_BACKEND_TYPE=DirectVulkan MOBILEGL_TRACE_OUTPUT=captures/mc26-full.trace /absolute/path/to/MobileGL/capture.sh
```

Reproduce the scene, leave several stable frames in the trace, then close the
game normally. Do not use `apitrace trace ./launch.sh`: that reverses preload
ordering and can cause the bridge to bypass the tracer.

List frames and trim one complete stable frame:

```sh
APITRACE="${MOBILEGL_APITRACE:-apitrace}"
"$APITRACE" dump --calls=frame captures/mc26-full.trace > captures/mc26-frames.txt
"$APITRACE" gltrim -f TARGET_FRAME \
  --output captures/mc26-frame.trace captures/mc26-full.trace
"$APITRACE" dump --calls=frame captures/mc26-frame.trace
```

Use the trimmed trace's final `glXSwapBuffers` call number as `TARGET_CALL`, then
replay the same input through both backends:

```sh
REPLAY_VK=build-vulkan/tools/trace_replay/mobilegl_trace_replay
REPLAY_WGPU=build-dawn/tools/trace_replay/mobilegl_trace_replay
"$REPLAY_VK" --backend DirectVulkan --mobilegl-library "$PWD/build-vulkan/libMobileGL.so" \
  --trace captures/mc26-frame.trace --target-call TARGET_CALL --output captures/vulkan
LD_LIBRARY_PATH="$PWD/build-dawn${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}" \
"$REPLAY_WGPU" --backend DirectWebGPU --mobilegl-library "$PWD/build-dawn/libMobileGL.so" \
  --trace captures/mc26-frame.trace --target-call TARGET_CALL --output captures/webgpu
python3 tools/native_harness/compare_frames.py \
  captures/vulkan/actual.png captures/webgpu/actual.png \
  --diff captures/vulkan-vs-webgpu.png --json captures/comparison.json
```

Preserve the full trace until the trimmed trace reproduces the incompatibility
on DirectWebGPU and renders correctly on DirectVulkan.

Command templates passed to `run_differential.py` must contain `{trace}`,
`{output}`, and `{call}`; `{output}` is a per-run directory and the replay must
write `actual.png` inside it. For example:

```sh
python3 tools/native_harness/run_differential.py \
  --trace work/1.20.1/trace.trace --target-call 280000 --localize \
  --reference-command 'build-vulkan/tools/trace_replay/mobilegl_trace_replay --backend DirectVulkan --mobilegl-library build-vulkan/libMobileGL.so --trace {trace} --target-call {call} --output {output}' \
  --candidate-command 'build-dawn/tools/trace_replay/mobilegl_trace_replay --backend DirectWebGPU --mobilegl-library build-dawn/libMobileGL.so --trace {trace} --target-call {call} --output {output}' \
  --output work/1.20.1/diff
```

Put Dawn's directory containing `libwebgpu_dawn.so` on `LD_LIBRARY_PATH` before
running the WebGPU command.
